# Faculty identity evidence: legacy parity and approved vNext constraint

The legacy faculty profile allowed profile-image and identity-document uploads through faculty-specific endpoints and direct file references (see `docs/legacy-source/frontend/src/components/profile/about.js:585-638,830-878`). The vNext security design does **not** accept raw client-supplied identity object keys or public URLs in a generic profile section PATCH.

The intended safe replacement is implemented at `src/app/api/people/faculty-self-document/identity/route.ts` and `src/modules/people/faculty-identity-evidence-service.ts`: an active faculty member requests a private, college-scoped upload; the object must match its ownership/size/content attestation and pass the clean-scan gate; a current receipt is stored atomically with profile version and audit event; reads require membership authorization, receipt ownership and a short-lived private grant; revocations make previous receipts unreadable. `src/modules/people/faculty-self-section-model.ts` forbids private receipt substitutions through generic PATCH.

For profile images, only a similarly authorized private-media replacement flow may set `profileImageDocumentId`; do not reintroduce legacy public links. The owner direction for this LMS build is signed-URL-only storage. Historical legacy images and identity evidence require a separately approved per-college migration plan before treating them as available: inventory old URL/key usage, securely import clean authorized documents and associate new private receipts with their original membership, verify replacement access, and depublicize legacy assets. This note does not claim that historical migration, production R2 configuration or depublication has been performed.

The UI may show masked summary and receipt status without disclosing the file key. An absent migration or unready private document storage must remain an explicit unavailable state; it must not silently manufacture or drop evidence.
