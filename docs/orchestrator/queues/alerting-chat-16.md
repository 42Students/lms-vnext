## What the old LMS does (read it, match behaviour; source in the legacy repo is summarised here)
- `TelegramNotifierService`: wrapper over Telegram Bot API `sendMessage`. Never throws (a notification failure must not break what triggered it). If token or chat id is unset it does nothing (debug log only). Plain text, no `parse_mode` (error text contains underscores and brackets that break Markdown). Outside production the text starts with the environment tag (`[dev] `) and there is no Acknowledge button (the bot's single webhook belongs to production). Config: `TELEGRAM_ALERT_BOT_TOKEN`, `TELEGRAM_ALERT_CHAT_ID`, `TELEGRAM_ALERT_WEBHOOK_SECRET` (already present in the dev `vnext-integrations` secret except the webhook secret, which vNext does not use outside production).
- `LogAlertingService`: finds ERROR+ entries since a cursor on a 2-minute schedule, exclusive via a scheduler lock. Only a genuinely NEW error signature alerts (message normalised then hashed, per environment); a known signature only updates counters (occurrences, first and last seen), no alert. Hard ceiling of 5 alerts per pass. A signature is persisted only after Telegram confirms delivery (so a failed send is retried next time). States: muted (known noise; a muted signature firing 25 or more times in one pass is reported as a spike), fixed (a fixed signature appearing again after 24 hours is reported as a regression), acknowledged. Alert text carries environment, time, route and count, plus blast radius (distinct accounts hit) where known.
- `LogDigestService`: a periodic digest of error counts (new, recurring, top signatures).
- `DeployHealthMonitor`: after a deploy, watches the new pods and alerts if they crash, restart or never become ready.
- `TelegramWebhookController`: production only; handles the Acknowledge button callback, checks `X-Telegram-Bot-Api-Secret-Token`.
- `ClientErrorReportController`: the browser reports front-end errors to the backend, which logs them with an `account=<id>/` marker so blast radius is known.
