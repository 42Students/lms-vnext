# Tenant row-level security: rollout

Written 2026-11-06. Design: [central-security-architecture.md](central-security-architecture.md), layer L5. This file is a runbook, not a status source; status lives in `docs/tracker.json`.

## What exists

| Piece | Where |
|---|---|
| Request-scoped database identity (user, college, role, platform, named system scope) | `src/db/tenant-context.ts` |
| Pool wrapper: applies the identity on checkout, resets it on release, destroys the connection if the reset fails | `src/db/tenant-pool.ts` (off unless `DB_TENANT_SCOPE=on`) |
| Route wrapper runs every authenticated handler inside the actor's scope | `src/security/route.ts` |
| Policy function `app_rls_allows(college_id)` and `tenant_isolation` policy on every table with `college_id` | `drizzle/0333_rls_tenant_policies.sql` (generated by `scripts/generate-rls-migration.mjs`) |
| CI guard: a new `college_id` table without a policy fails `security:central` | `scripts/check-security-central.mjs` |
| Executed proof on disposable PostgreSQL 17 with a non-superuser role | `scripts/rls-tenant-acceptance.mjs` (CI `database` job) |

## Why it is inert today

`app_rls_allows` returns true unless the database setting `app.rls_mode` is `enforce`. Merging the migration therefore changes no behaviour. Enforcement is a separate, human-gated step per environment.

## Before enforcing in any environment

1. **Scope coverage.** About 800 routes are not on the wrapper yet, and server components, jobs and the session/membership bootstrap run outside it. In enforce mode an unset scope sees no rows. Every such path must either run inside `runWithTenantScope` or, for internal jobs and bootstrap reads, inside `runAsSystem("<reason>")`. Convert them first; `security:central` tracks the route count.
2. **Per-table review.** Some tables hold intentionally shared rows (`college_id` NULL), recruiter grants that cross colleges, or Super Admin reads. The single policy hides NULL-college rows and cross-college recruiter reads. Each such table needs a reviewed policy variant before enforcement.
3. **Runtime role.** It must be neither superuser nor `BYPASSRLS` (production already refuses otherwise, `src/db/runtime-principal-policy.ts`). Table owners are exempt unless `FORCE ROW LEVEL SECURITY` is added; the migration role must stay an owner so migrations and backfills work.
4. **Performance.** With `DB_TENANT_SCOPE=on` each checkout in a scoped request adds one `set_config` round trip and each release one reset. Measure on dev first.

## Enabling (dev first, never production from this runbook)

```
-- per environment, by a human, after the checks above
ALTER DATABASE <name> SET app.rls_mode = 'enforce';
-- and in the app environment
DB_TENANT_SCOPE=on
```

Roll back with `ALTER DATABASE <name> RESET app.rls_mode;` (new connections pick it up) and unset `DB_TENANT_SCOPE`.

## What the acceptance script proves

- every table with `college_id` has RLS enabled and the `tenant_isolation` policy;
- inert mode: all rows visible;
- enforce mode: no scope sees nothing; college A sees only A; college B only B; platform and named system scopes see all;
- enforce mode: college A cannot insert a college B row, and can insert its own.

It proves the policy mechanics. It does not prove that application code sets the scope everywhere; that is step 1 above and is verified route by route.

## Dev findings 2026-11-07 (read from the live dev database, read-only job)

- The runtime role `lms_vnext_app` is not a superuser and has no BYPASSRLS, but it OWNS all 278 tables and has CREATEROLE and CREATEDB. Table owners ignore RLS unless the table is `FORCE`d, so enforcement would have protected nothing. Migration `0337_rls_force_for_owner.sql` forces RLS on every table that has the `tenant_isolation` policy (the generator now emits FORCE for new tables). Still inert until the mode is `enforce`.
- The role is not the database owner (`cloudsqlsuperuser` is), so `ALTER DATABASE ... SET app.rls_mode` is not available to it. Enforcement is therefore set per process: the web Deployment gets `PGOPTIONS=-c app.rls_mode=enforce` (node-pg reads `PGOPTIONS`). The migrator Job and CronJobs do not set it, so they are not subject to the policies. Rollback: unset `PGOPTIONS` on the Deployment.
- Real fix for production: a separate owner role for migrations and a runtime role that owns nothing and has no CREATEROLE or CREATEDB (SEC-06-011, SEC-06-012). FORCE is the interim guard, not a replacement.
- Zero `SECURITY DEFINER` functions. 113 tables have RLS enabled, 115 policies, 165 tables have no `college_id` (parent-derived tenancy still to be listed, SEC-06-003).

## Dev enforcement ON since 2026-11-07 (image c35cfbfe)

Web pods in `lms-dev-2026` run with `DB_TENANT_SCOPE=on`, `SECURITY_SHARED_STORE=on`, `PGOPTIONS=-c app.rls_mode=enforce`, `DB_POOL_MAX=10` (also in `deploy/k8s/dev/lms-vnext-deployment.yaml`). Migration 0337 applied (113 tables RLS-enabled and forced).

- Executed probe against the real dev database with the real runtime role and `app.rls_mode=enforce` (read-only job, rolled back): system scope sees 171 membership rows; no scope sees 0; college A sees only its own 154 and 0 of college B's; update and delete of college B rows affect 0 rows; platform scope sees all; a malformed college id errors instead of widening access. This is manual evidence, not CI evidence.
- First attempt with all three switches and `DB_POOL_MAX=3` made the pod unready (`timeout exceeded when trying to connect`): the shared store adds one database call per request and 3 connections were not enough. Rolled back within minutes, then re-enabled in two steps (scope plus enforce, then shared store with pool 10). Stable since; login pages 200 on vnext, testa, testb; no connection timeouts in the pod log.
- NOT yet tested under enforcement: signed-in pages and APIs (no test login performed), background CronJobs (they do not set PGOPTIONS, so they are not enforced). Click-through of each role is the next check, at the CI/e2e pass.
- Rollback: delete the three variables from the Deployment (`kubectl set env deployment/lms-vnext DB_TENANT_SCOPE- SECURITY_SHARED_STORE- PGOPTIONS-`).

## Build complete, not yet deployed (2026-11-07, later): parent-derived policies, role split, probes

Written, not applied to any database, not tested (tests and CI run once, at the end):

- **Migration `0338_rls_derived_policies.sql`**: 127 child tables (the 125 foreign-key-derived ones plus `placement_learner_requests` and `learner_profile_education_documents`, anchored by hand on `learner_membership_id`) get RLS, FORCE and a policy `tenant_isolation_derived`: `app_rls_bypass() OR EXISTS (SELECT 1 FROM <parent> p WHERE p.<pk> = child.<fk>)`, with the parent's own policy applying inside the lookup. Anchors were read from the live dev catalog, shortest path first, no cycles (chain depth at most 6). The plan is [derived-policy-plan.json](assessments/derived-policy-plan.json). New function `app_rls_bypass()` is the same rule as `app_rls_allows` minus the college clause (inert, platform scope, named system scope). Inert until `app.rls_mode=enforce`, which dev already has, so applying 0338 to dev takes effect at once.
- **Deliberately not given a policy** (reviewed list: [table-classification.json](table-classification.json)): `users`, `organizations`, `colleges`, `membership_roles`, `module_access_rules` (identity core; narrowing needs a per-query review because sign-in, the college picker, recruiter views and Super Admin pages read them across colleges); user-owned tables (`identity_device_sessions`, `system_roles`, recruiter profiles and contacts, platform broadcasts), where admins act on other users' rows through several services; infrastructure and platform reference tables (job leases, shared store, log alerts, audit findings, bug tracker, skills, outbound suppressions, platform settings, project templates, placement company master). `security:central` now fails a new table that is in none of: has `college_id` plus policy, derived plan, classification file.
- **Role split (SEC-06-011/012), owner-gated, needs a `cloudsqlsuperuser` login that I do not hold:** create `lms_vnext_migrator` (owns all tables, runs migrations), keep `lms_vnext_app` as login-only with no CREATEROLE, no CREATEDB, no ownership; `REASSIGN OWNED BY lms_vnext_app TO lms_vnext_migrator`; `GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO lms_vnext_app`; `ALTER DEFAULT PRIVILEGES FOR ROLE lms_vnext_migrator IN SCHEMA public GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO lms_vnext_app`; sequences likewise; point the migrator Job at the owner secret. FORCE (0337) keeps dev protected until then. Never done on production from here.
- **Dynamic SQL (SEC-06-018):** every `sql.raw()` outside `src/db/schema` takes a fixed literal except `shared-store-core.ts`, whose strings are module constants with user values only as bound parameters. New rule `sql-raw-dynamic` makes any other dynamic use fail `security:central`.
- **Probes for the final run:** `scripts/rls-isolation-sweep.mjs` (every policied table: no scope sees nothing, colleges A and B disjoint, no foreign-stamped rows) and `scripts/rls-perf-probe.mjs` (inert vs enforced timing, budget 1.5x plus 2 ms). `scripts/rls-tenant-acceptance.mjs` gained update, delete, row-move, derived-child, FORCE and no-SECURITY-DEFINER checks.
- **Jobs and scheduled work (SEC-05-013):** the eight internal job routes run in one named system scope each (`internalRoute`), so they are not narrowed by RLS by design; any tenant selection happens inside the job service. CronJobs do not set `PGOPTIONS`, so they are not enforced at all.

## Identity core and module rules (migrations 0339, 0340), written 2026-11-07

- `0339`: a person always sees their own memberships (`own_memberships`, SELECT only); `colleges` = the active college or any college with a visible membership; `organizations` = through a visible college; `users` = self, anyone with a visible membership, or a recruiter; `membership_roles` follows its membership. Writes need platform or system scope, or the actor's own college or user row.
- `0340`: `module_access_rules` follow their scope target (college, organization, membership, section, cohort, program, department); GLOBAL rules are readable by every college and writable only by platform or system scope.
- Watch on dev after applying: sign-in, workspace picker, college and organization names in headers, recruiter names on TPO pages, Super Admin pages. Rollback: `ALTER TABLE <t> NO FORCE ROW LEVEL SECURITY; DROP POLICY ...` per table, or unset `PGOPTIONS` on the Deployment to switch enforcement off.
- Jobs (SEC-05-013): the eight internal job routes and the CronJobs authenticate by secret and run unscoped by design (named system scope, or not enforced); each job takes `college_id` from the rows it processes. CronJobs get enforcement only if they are moved onto `internalRoute`.
