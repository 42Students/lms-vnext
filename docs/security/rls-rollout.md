# Tenant row-level security: rollout

Written 2026-11-06. Design: [central-security-architecture.md](central-security-architecture.md), layer L5. This file is a runbook, not a status source; status lives in `docs/tracker.json`.

## What exists

| Piece | Where |
|---|---|
| Request-scoped database identity (user, college, role, platform, named system scope) | `src/db/tenant-context.ts` |
| Pool wrapper: applies the identity on checkout, resets it on release, destroys the connection if the reset fails | `src/db/tenant-pool.ts` (off unless `DB_TENANT_SCOPE=on`) |
| Route wrapper runs every authenticated handler inside the actor's scope | `src/security/route.ts` |
| Policy function `app_rls_allows(college_id)` and `tenant_isolation` policy on every table with `college_id` | `drizzle/0333_rls_tenant_policies.sql` (generated by `scripts/generate-rls-migration.mjs`) |
| CI guard: a new `college_id` table without a policy fails `security:central` | `scripts/check-security-central.mjs` |
| Executed proof on disposable PostgreSQL 17 with a non-superuser role | `scripts/rls-tenant-acceptance.mjs` (CI `database` job) |

## Why it is inert today

`app_rls_allows` returns true unless the database setting `app.rls_mode` is `enforce`. Merging the migration therefore changes no behaviour. Enforcement is a separate, human-gated step per environment.

## Before enforcing in any environment

1. **Scope coverage.** About 800 routes are not on the wrapper yet, and server components, jobs and the session/membership bootstrap run outside it. In enforce mode an unset scope sees no rows. Every such path must either run inside `runWithTenantScope` or, for internal jobs and bootstrap reads, inside `runAsSystem("<reason>")`. Convert them first; `security:central` tracks the route count.
2. **Per-table review.** Some tables hold intentionally shared rows (`college_id` NULL), recruiter grants that cross colleges, or Super Admin reads. The single policy hides NULL-college rows and cross-college recruiter reads. Each such table needs a reviewed policy variant before enforcement.
3. **Runtime role.** It must be neither superuser nor `BYPASSRLS` (production already refuses otherwise, `src/db/runtime-principal-policy.ts`). Table owners are exempt unless `FORCE ROW LEVEL SECURITY` is added; the migration role must stay an owner so migrations and backfills work.
4. **Performance.** With `DB_TENANT_SCOPE=on` each checkout in a scoped request adds one `set_config` round trip and each release one reset. Measure on dev first.

## Enabling (dev first, never production from this runbook)

```
-- per environment, by a human, after the checks above
ALTER DATABASE <name> SET app.rls_mode = 'enforce';
-- and in the app environment
DB_TENANT_SCOPE=on
```

Roll back with `ALTER DATABASE <name> RESET app.rls_mode;` (new connections pick it up) and unset `DB_TENANT_SCOPE`.

## What the acceptance script proves

- every table with `college_id` has RLS enabled and the `tenant_isolation` policy;
- inert mode: all rows visible;
- enforce mode: no scope sees nothing; college A sees only A; college B only B; platform and named system scopes see all;
- enforce mode: college A cannot insert a college B row, and can insert its own.

It proves the policy mechanics. It does not prove that application code sets the scope everywhere; that is step 1 above and is verified route by route.

## Dev findings 2026-11-07 (read from the live dev database, read-only job)

- The runtime role `lms_vnext_app` is not a superuser and has no BYPASSRLS, but it OWNS all 278 tables and has CREATEROLE and CREATEDB. Table owners ignore RLS unless the table is `FORCE`d, so enforcement would have protected nothing. Migration `0337_rls_force_for_owner.sql` forces RLS on every table that has the `tenant_isolation` policy (the generator now emits FORCE for new tables). Still inert until the mode is `enforce`.
- The role is not the database owner (`cloudsqlsuperuser` is), so `ALTER DATABASE ... SET app.rls_mode` is not available to it. Enforcement is therefore set per process: the web Deployment gets `PGOPTIONS=-c app.rls_mode=enforce` (node-pg reads `PGOPTIONS`). The migrator Job and CronJobs do not set it, so they are not subject to the policies. Rollback: unset `PGOPTIONS` on the Deployment.
- Real fix for production: a separate owner role for migrations and a runtime role that owns nothing and has no CREATEROLE or CREATEDB (SEC-06-011, SEC-06-012). FORCE is the interim guard, not a replacement.
- Zero `SECURITY DEFINER` functions. 113 tables have RLS enabled, 115 policies, 165 tables have no `college_id` (parent-derived tenancy still to be listed, SEC-06-003).

## Identity core and module rules (migrations 0339, 0340), written 2026-11-07

- `0339`: a person always sees their own memberships (`own_memberships`, SELECT only); `colleges` = the active college or any college with a visible membership; `organizations` = through a visible college; `users` = self, anyone with a visible membership, or a recruiter with a grant the college can see; `membership_roles` follows its membership. Writes need platform or system scope, or the actor's own college or user row.
- `0340`: `module_access_rules` follow their scope target (college, organization, membership, section, cohort, program, department); GLOBAL rules are readable by every college and writable only by platform or system scope.
- Watch on dev after applying: sign-in, workspace picker, college and organization names in headers, recruiter names on TPO pages, Super Admin pages. Rollback: `ALTER TABLE <t> NO FORCE ROW LEVEL SECURITY; DROP POLICY ...` per table, or unset `PGOPTIONS` on the Deployment to switch enforcement off.
- Jobs (SEC-05-013): the eight internal job routes and the CronJobs authenticate by secret and run unscoped by design (named system scope, or not enforced); each job takes `college_id` from the rows it processes. CronJobs get enforcement only if they are moved onto `internalRoute`.

## Signed-in click-through under enforcement, 2026-11-07 (dev, image 356deba9) and the three bugs it found

Signed in on https://vnext.development.42lms.com with the seeded test accounts (dev only). With `DB_TENANT_SCOPE=on`, `SECURITY_SHARED_STORE=on` and `PGOPTIONS=-c app.rls_mode=enforce` all running, these now work:

- College admin (TESTA): dashboard (college, departments, people counts), 16 `/college/*` pages (all 200, real data), the Departments, Programs and Courses pages (hard load and in-app navigation), the workspace API.
- Learner (7 pages), faculty (6), mentor (2 real pages), TPO (5), recruiter and Super Admin (`/api/colleges` lists every college, `/admin/colleges`, `/admin/courses`, `/admin/features`, `/admin/audit` with rows). The shared faculty with TESTA and TESTB memberships saw both in the workspace picker before any college was chosen, then selected one.
- Sign-in itself: email code request, code verification, SUPER_ADMIN second code.

Bugs found by doing this and fixed (none showed up in the database-level sweep, which is why clicking was necessary):

1. **Pool wrapper leaked every unscoped query (`src/db/tenant-pool.ts`).** pg-pool's own `query()` calls `this.connect(callback)`; the wrapper replaced `connect` and ignored the callback, so each such query held a connection forever until the pool was empty and requests hung (the pod looked idle, the database showed idle sessions, no log lines). It also explains why the first attempt with all switches on and a small pool failed on 2026-11-07. Fixed to honour the callback form; reproduced and verified against the dev database with a 2-connection pool; regression tests added in `tests/unit/tenant-pool.test.ts`.
2. **Host-to-college lookup and the login page ran with no scope (`resolveRequestTenant`, `src/app/page.tsx`).** Under enforcement a college host showed "This address isn't set up yet". Both now run in a named system scope (`tenant:resolve-host`, `public-page:login`).
3. **Sibling server components had no scope.** Next renders layouts, pages and Suspense children in separate async chains, so the AsyncLocalStorage holder opened by one did not reach the others. `tenant-context.ts` now also keeps the actor scope in React's per-request cache and reads it as a fallback (ALS scope still wins).

Other dev findings: `testa` and `testb` are not routed to vNext on the dev ingress (only `vnext` and `nsrit` are); they land on the legacy app, so college logins on dev use the platform host and choose the college after sign-in. The shared store is back ON (it was only ever off because of bug 1).
