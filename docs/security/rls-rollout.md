# Tenant row-level security: rollout

Written 2026-11-06. Design: [central-security-architecture.md](central-security-architecture.md), layer L5. This file is a runbook, not a status source; status lives in `docs/tracker.json`.

## What exists

| Piece | Where |
|---|---|
| Request-scoped database identity (user, college, role, platform, named system scope) | `src/db/tenant-context.ts` |
| Pool wrapper: applies the identity on checkout, resets it on release, destroys the connection if the reset fails | `src/db/tenant-pool.ts` (off unless `DB_TENANT_SCOPE=on`) |
| Route wrapper runs every authenticated handler inside the actor's scope | `src/security/route.ts` |
| Policy function `app_rls_allows(college_id)` and `tenant_isolation` policy on every table with `college_id` | `drizzle/0333_rls_tenant_policies.sql` (generated by `scripts/generate-rls-migration.mjs`) |
| CI guard: a new `college_id` table without a policy fails `security:central` | `scripts/check-security-central.mjs` |
| Executed proof on disposable PostgreSQL 17 with a non-superuser role | `scripts/rls-tenant-acceptance.mjs` (CI `database` job) |

## Why it is inert today

`app_rls_allows` returns true unless the database setting `app.rls_mode` is `enforce`. Merging the migration therefore changes no behaviour. Enforcement is a separate, human-gated step per environment.

## Before enforcing in any environment

1. **Scope coverage.** About 800 routes are not on the wrapper yet, and server components, jobs and the session/membership bootstrap run outside it. In enforce mode an unset scope sees no rows. Every such path must either run inside `runWithTenantScope` or, for internal jobs and bootstrap reads, inside `runAsSystem("<reason>")`. Convert them first; `security:central` tracks the route count.
2. **Per-table review.** Some tables hold intentionally shared rows (`college_id` NULL), recruiter grants that cross colleges, or Super Admin reads. The single policy hides NULL-college rows and cross-college recruiter reads. Each such table needs a reviewed policy variant before enforcement.
3. **Runtime role.** It must be neither superuser nor `BYPASSRLS` (production already refuses otherwise, `src/db/runtime-principal-policy.ts`). Table owners are exempt unless `FORCE ROW LEVEL SECURITY` is added; the migration role must stay an owner so migrations and backfills work.
4. **Performance.** With `DB_TENANT_SCOPE=on` each checkout in a scoped request adds one `set_config` round trip and each release one reset. Measure on dev first.

## Enabling (dev first, never production from this runbook)

```
-- per environment, by a human, after the checks above
ALTER DATABASE <name> SET app.rls_mode = 'enforce';
-- and in the app environment
DB_TENANT_SCOPE=on
```

Roll back with `ALTER DATABASE <name> RESET app.rls_mode;` (new connections pick it up) and unset `DB_TENANT_SCOPE`.

## What the acceptance script proves

- every table with `college_id` has RLS enabled and the `tenant_isolation` policy;
- inert mode: all rows visible;
- enforce mode: no scope sees nothing; college A sees only A; college B only B; platform and named system scopes see all;
- enforce mode: college A cannot insert a college B row, and can insert its own.

It proves the policy mechanics. It does not prove that application code sets the scope everywhere; that is step 1 above and is verified route by route.
