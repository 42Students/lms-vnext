# vNext Telegram alerting — operational runbook (GR-111–GR-125)

This is an **implementation/operations guide**, not evidence of successful rollout. Never print bot tokens, webhook secrets, HMAC keys or database passwords. Do not commit secret files. The bot's webhook belongs to **production only**.

## 1. Prerequisites

- Register and replay `docs/proposed-migrations/graceful-telegram-alerting.sql` through the single-writer DB10 migration process. It proposes `log_alert_signatures`, `log_alert_signature_accounts`, `log_alert_states`, `log_alert_daily_counts`, `log_alert_observed_events` and `scheduled_job_leases` plus additive Cloud Logging page/window checkpoint columns.
- Confirm the registered migration, constraints, and clean replay on disposable PostgreSQL; only then set `DB10_LOG_ALERTS_READY=DB10_VERIFIED`. Do not enable based on schema drafts or unit tests alone.
- Configure `TELEGRAM_ALERT_BOT_TOKEN` and `TELEGRAM_ALERT_CHAT_ID` in an external secret store. For production, also set `TELEGRAM_ALERT_WEBHOOK_SECRET` and register exactly one Telegram webhook to `/api/webhooks/telegram` with the matching secret-token header. The callback must originate from `TELEGRAM_ALERT_CHAT_ID` and carry a Telegram message chat ID; callbacks from other chats are deliberately ignored. **Never configure the Telegram production webhook against dev/UAT.**
- Set `LOG_ALERT_ACCOUNT_HASH_KEY` from the secret store to enable privacy-preserving per-account blast-radius counting. Without it, alerts work but affected-account counts may be zero.
- To enable collection of ERROR-level Cloud Logging entries missed by in-process callbacks, explicitly set `LOG_ALERT_CLOUD_POLL_ENABLED=true`, `GOOGLE_CLOUD_PROJECT`, and `LOG_ALERT_K8S_NAMESPACE` (required in production). Grant the web workload identity minimal Cloud Logging `logging.logEntries.list` permission on **that project only** and metadata-server token access. Query scope is restricted to the configured Kubernetes namespace and the `web` container. The reader handles at most two 12-entry pages per tick and stores a durable page token with a fixed timestamp window, so identical-timestamp entries cannot be skipped at the batch boundary; Cloud Logging failures must not block the digest. Until opt-in and IAM smoke verification, the Logs page indicates that the backup is unconfigured. The reporter stores only a SHA-256 fingerprint of the environment, signature and validated request reference to deduplicate in-process/Cloud reports; 30-day retention prunes those fingerprints after a successful daily job. Logs lacking a reliable request reference cannot be deduplicated across these paths and must not be used as a billing-grade metric.
- Provision a strong `INTERNAL_ALERT_TICK_SECRET` accessible to the in-cluster tick CronJob and web service, not to browsers or public clients.
- Independent health-watch requires an accessible PostgreSQL `DATABASE_URL` supplied securely to its pod, which may differ from the web pod's Cloud SQL Unix-socket configuration. Restrict database privileges to the necessary lease table. Never put the URL into Kubernetes YAML. For a full cluster/DB outage, arrange an **external** Telegram-connected uptime monitor; this CronJob cannot persist state when its database is inaccessible.

## 2. Deploy and check

Apply the new manifests under `deploy/k8s/dev/alerting/` to the **dev namespace only**, after the secrets, service DNS and migration are ready. The two-minute tick calls `POST /api/internal/alerts/tick` with the internal secret; the separate one-minute health watch checks the service's `/ready` and `/` independently of web pods. Two consecutive failed checks should send a Telegram outage alert; the next good check sends a recovery alert. Test both without affecting shared/production traffic.

The orchestrator runs `scripts/ops/deploy-health-check.sh` after each rollout with `READY_URL` set to the deployed `/ready` address. It fails the deploy-health step on rollout failure, restarts, zero ready replicas or failed readiness. Telegram status posts are best-effort and never make a previously failed rollout look healthy. Do not paste environment variables into issue comments or CI logs.

At or after **09:00 IST**, the first successful tick sends the digest for the completed prior IST day. It includes new/recurring counts, top-five signatures, muted counts, spikes, deploy commit when provided, and current health-watch state. The global state row limits error bursts to five posts per minute and preserves suppressed known-signature counts for a later tick. A NEW signature suppressed by the cap stays retryable instead of being counted repeatedly as overflow. Validated server-generated daily dates and commit/signature hashes remain visible in Telegram; free-form error text remains redacted. A scheduled regression sweep handles fixed errors with eligible, previously undelivered recurrences.

## 3. Acceptance / escalation

The orchestrator must run typecheck, lint, unit tests (including the fake Telegram HTTP server), disposable PostgreSQL integration tests and in-cluster smoke checks; then verify actual production-only Acknowledge callbacks. Validate that sensitive strings never enter alerts and that test messages from development begin with `[vnext dev]`. Review `docs/audit/acceptance/graceful-alerting-verification.md` for GR-by-GR source and test evidence; none of these tests were executed by builder chat-16.

To investigate an alert: use its short request ID in structured application logs; open **42 Tracker → Known Errors** for the signature, counts, affected-account estimate and triage actions. Mute known noise, mark a fixed regression only after deploying the fix, and use Acknowledge in production. Never copy raw provider responses, secrets or account identities into Telegram or support tickets.

When alerts seem silent, inspect, in order: environment configuration status on Logs, migration readiness flag, tick CronJob status, health-watch pod/reachability, Telegram Bot API connectivity, and whether the signature is already known/muted or burst-capped. Known signatures are intentionally silent except volume spikes and fixed regressions. If Telegram is temporarily unavailable, new signatures are **not** marked delivered; retry occurs on a later occurrence and eligible regressions are swept by the tick.

## Telegram webhook registration and rotation

The webhook is an operator-approved **production-only** deployment step, never an on-request side effect. After registered DB10 schema readiness and workload secrets are verified, register `https://<production-host>/api/webhooks/telegram` using Telegram Bot API `setWebhook`, with `secret_token` equal to the deployed `TELEGRAM_ALERT_WEBHOOK_SECRET`, `allowed_updates` limited to `callback_query`, and `drop_pending_updates=false` unless the operator intentionally discards old callbacks. Use secret-store-injected environment values and suppress verbose shell logging (especially `set -x`); do not paste token-bearing API URLs or headers into audit files.

Verify with `getWebhookInfo` from a protected operator terminal that `url` matches the production host, `pending_update_count` is stable, and recent delivery errors are absent. Send a redacted production test alert and confirm the inline button reads **✅ Acknowledge**. After tapping, verify that the original Telegram message ends once with a blank line and **✅ Acknowledged**, the inline keyboard is gone, and the database `acknowledged_at` is unchanged on a second tap. Non-UUID legacy `ack:` payloads deliberately return a neutral callback answer: only a known production signature UUID may mutate state.

For rotation, stage new bot/webhook secrets together, update the production workload and its matching `setWebhook` secret within a controlled change window, verify the new header and chat, then revoke the old secret. A provider edit failure is best-effort after a committed acknowledgment; a retry tap may repair the message edit, and a DB error returns HTTP 503 without asserting a successful acknowledgment. None of these steps is evidence of a completed production deployment or tested provider delivery.
